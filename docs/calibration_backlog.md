## 1. 既知の制限（設計上の穴。パラメータ調整では解決しない）

### 1-1. S6 / 本体S2 の在庫両義判定は実データで「シグナルなし」に退行する

原価の数量／価格分解（`cogs_quantity` / `cogs_price`）は、**本体にも実XBRLにも

### 1-1b. 単一レジームへの過剰適合リスク

**パラメータ校正は 2023〜2024年の単一レジームのデータに基づく。** バックテスト窓が
その期間に確定するのは、四半期単独値を作れるのが EDINET 四半期報告書のある
FY2023〜FY2024 に限られるため（制度は 2024-04-01 以後開始の四半期から廃止）。

同一の相場環境・金利環境・為替環境のデータだけで閾値を決めると、環境が変わった
瞬間に効かなくなる。**TDnet の前向き蓄積が進んだ時点で、第2レジーム（2026年以降）
での再検証を必ず行うこと。** 5四半期深度への到達は約15ヶ月後（2027年11月頃）。

再検証前に運用へ乗せる場合は、校正値を「暫定」と明示し、ポジションサイズを
抑えること。第2レジームで再現しなかった指標は落とす。

**2026-09-01 追記**: 実際の窓は 2021-09-01〜2026-08-31（1,222営業日）まで広がり、
四半期イベントは 20,810 件を確保できた。ただし 4-3 の診断のとおり、この窓には
**2024年8月の急落（TOPIX 20営業日で -22.8%）という単一の大きなイベント**が
含まれ、最大ドローダウンはほぼそれ1回で決まっている。窓が5年に伸びても
「レジームの数」が増えたわけではない点は変わらない。

### 1-2. 日次株価が2年分ない

**2026-08-31 実測**: 無料プランの提供範囲は API が明示している ——
`Your subscription covers the following dates: 2024-06-08 ~ 2026-06-08`
（2年ローリング + 12週遅延）。2024-06-07 以前は HTTP 400 で取得できない。

これは財務データ側の窓と**噛み合わない**。EDINET 四半期報告書から作れる
連続四半期は FY2023〜FY2024（2022-04〜2024-03）で、**株価が1日も重ならない**。

| プラン | 月額 | 遡及 | TOPIX |
|---|---:|---|---|
| Free | ¥0 | 2年（直近12週を除く） | **含まれない** |
| Light | ¥1,650 | 5年 | 含まれる |
| Standard | ¥3,300 | 10年 | 含まれる |
| Premium | ¥16,500 | 20年 | 含まれる |

2022年以降の株価と TOPIX を揃えるには **Light 以上が必要**。

**2026-08-31: Light 加入により解消。** 実測した提供範囲は **2021-08-31 〜**
（株価 `/equities/bars/daily`・TOPIX `/indices/bars/daily/topix` とも同じ境界。
2021-08-30 以前は HTTP 400）。EDINET 四半期報告書から作れる窓（2022-04〜2024-03）を
完全に覆う。TOPIX は 1,223営業日を取得済み。

**配信遅延について（2026-09-02 確認）**: 上表の「12週遅延」は**無料プラン
固有の制限**であり、Light 以上には適用されない。公式仕様では **Light 以上は
株価・TOPIX とも当日 16:30 頃に当日分が配信される**。したがって
**リアルタイム性を理由とした Standard へのアップグレードは不要**。

裏付け（実測）: 2026-09-01 11:28 に流したバックフィルが 2026-08-31 分まで
取得できている。12週遅延なら 2026-06 上旬までしか取れないので、
遅延が無いことは実データ側からも確認できる。

**運用上の含意**: ペーパートレードの週次バッチは、前営業日の終値・
TOPIX 200日移動平均を当日朝の時点で参照できる。遅延を織り込んだ
特別な設計は要らない。

### 1-2b. 決算発表日は EDINET 提出日の代理

J-Quants の `/equities/earnings-calendar` は**将来の予定日のみ**で、過去実績を返さない
（2026-08-31 実測: 1件のみ）。T-15 エントリー / T+N エグジットの営業日計算には実際の
発表日が要るので、**EDINET の提出日を短信発表日の代理**として使う。

**現行制度（有報・半期報告書）での実測（2026-09-01、543組）**:

決算期（`(証券コード, 決算期末年月, 四半期区分)`）で突合。近接マッチだと乖離の
大きいペアが機械的に除外され、測定値が過小に出るため使わない。

| 差 | 暦日 | 比率 | 営業日 | 比率 |
|---:|---:|---:|---:|---:|
| +0 | 359 | **66.1%** | 359 | **66.1%** |
| +1 | 56 | 10.3% | 79 | 14.5% |
| +2 | 13 | 2.4% | 18 | 3.3% |
| +3 | 32 | 5.9% | 14 | 2.6% |
| +4以上 | 69 | 12.7% | 59 | 10.9% |

中央値 **+0日**、平均 +0.27日、最大 +32日。**0〜3営業日以内が86.6%**、
**|差| > 3営業日が13.4%**。内訳は半期報告書517組・有価証券報告書26組。
（標本の97%が半期報告書。四半期報告書に対する代理として最も近い制度形態。）

**直接測定は不可能と確定（2026-09-01）**: バックテスト対象である四半期報告書での
乖離は、**原理的に測れない**。TDnet の保持は約1ヶ月で、ローカルに残る短信は
**2026-07-23 以降の 4,172 件のみ**。四半期報告書の対象期（2022-06〜2024-03）には
短信が1件も存在せず（実測 0 件）、EDINET 側をいくら遡っても対になる相手がいない。
「EDINET バックフィル完了後に再測定」という当初の想定は、律速が EDINET ではなく
**TDnet の保持期間**だったという点で誤りだった。バックフィルは完了したが、この項目は
それでは解消しない。

**代替（2段構え）**:

1. **大標本での実測**（上表）。212組 → 543組へ拡大。結論は変わらず中央値0日。
2. **発表日ずらし感度分析**。代理発表日を **-3 / 0 / +3 営業日**ずらした3パターンで
   バックテストを回し、期待値・勝率が大きく変わらないことを確認する。頑健なら
   「代理日の誤差は戦略の結論を変えない」と構造的に言える。±3で崩れるなら保留。
   なお上表のとおり **|差| > 3営業日が13.4%** 残るので、±3 は全数を覆う保証ではなく
   「主要部分に対する頑健性」の検証である点は明示しておく。

### 1-3. PTS 出来高のデータソースが無い

**状態**: 「当面は取得せず、翌日寄り指値固定」の fallback を承認済み（2026-08-31）。

## 1-6. ローカルDBが唯一の正本 —— バックアップは必須構成要素

**J-Quants Light は5年ローリング窓**（2026-09-01 時点で 2021-08-31 〜）。窓から
落ちた日付は**二度と取得できない**。同じことが EDINET の生 zip（現行の索引窓の
外は取り直しに時間がかかる）と TDnet の短信（約40日で消える）にも当てはまる。

したがって `DATA_ROOT`（`D:\screener_data`）は**再生成できない一次資料**であり、
**ローカルDBが唯一の正本**。バックアップは「あれば良いもの」ではなく、
**システムの必須構成要素**である。

派生する運用規則:

- 取得時は「今は使わない列」も落とさない。窓から落ちてからでは足せない
  （2026-08-31 に始値・調整後株価・時価総額の保存漏れを発見し取り直した）
- `DATA_ROOT` は git 管理外なので、バックアップ対象として明示的に運用へ組み込む
- バックアップ先は**別の物理ディスク**。同一ディスク上のコピーは誤削除対策に
  しかならず、ディスク故障では一緒に失う（`backup_data.ps1` が構造的に拒む）
- 稼働中の SQLite は robocopy でコピーしない。backup API で一貫コピーを作る

**2026-09-01 時点の状態: バックアップ先が存在せず未稼働。** スクリプト
（`screener/backup_data.ps1` / `install_backup_task.ps1`）は用意済みだが、
このマシンは物理ディスクが1台（Disk 0）だけで、C:(空き3GB) / D:(元) / G:(Google
Drive 空き2.9GB) のいずれも要件を満たさない。**外付けドライブの調達が要る。**

### 4-3. ドローダウンの診断（再判定ではなく原因の解剖）

**結論: 独自要因ではなく、2024年8月の日本株急落に巻き込まれた形。**

- **谷の位置**: 山 2024-07-12 → 底 2024-12-20 → 回復 2025-08-14（約8ヶ月）
- **同期間のトレード**: 160件(全体の9.2%)、平均 -1.18% / 勝率40.0%
  （全期間は平均 +2.09% / 勝率53.8%）
- **市場全体の動き**: 同期間の TOPIX は -6.65%。ただし内訳は
  **7/12→8/5 が -23.06%**、その後 8/5→12/20 が +21.32%。
  TOPIX の全期間最大下落局面を機械的に探すと、5/20/60営業日のいずれの窓でも
  **底が 2024-08-05 の同一局面**（-19.30% / -22.78% / -18.37%）。
- **月別**: 最悪は 2024-08（30件・平均 -6.76%・勝率27%）、次いで
  2024-10（13件・平均 -5.39%・勝率23%）。
- **セクター**: 谷の期間で悪いのは機械 -5.53% / 化学 -5.24% / 電気機器 -4.29% だが、
  **いずれも件数6〜14件**。事前登録 §4 の「1層100件未満は合否材料にしない」に該当し、
  セクター要因とは言えない。
- **利益集中度は低い(7.0%)** = 勝ちは分散している。負けだけが特定局面に集中。

**市場環境別に見ると構造が一貫している**:

| 市場環境 | 件数 | 平均 | 勝率 |
|---|---|---|---|
| 上昇相場 | 1,559 | +2.40% | 54.8% |
| 下降相場 | 183 | -0.48% | 45.9% |

上昇相場で機能し下降相場で期待値がマイナスに転じる、**市場ベータをそのまま被った
ロングオンリー戦略**の姿。ヘッジも市場フィルタも持っていないので当然ではある。

### 4-4. 資産曲線の前提に無理がある（要検討・今回は判定に影響させない）

同日エントリー数は**中央値2件に対し最大117件**（2026-07-16）。決算発表が集中する
時期にシグナルが束で立つ。これを「1トレード=NAV10%固定・最大10ポジション想定」で
資産曲線に流すと、**実際には建てられない建玉**を前提に MDD が算出される。

つまり **-32.3% という数字自体が、実行不能なポジションサイジング下での値**である
可能性が高い。ただし事前登録 §2 が定めた計算方法そのものなので、
**判定は不合格のまま動かさない**。

次にやるべきは基準の緩和ではなく、**ポジションサイジングの設計**（同時保有上限、
1日あたりの新規建玉上限、シグナル集中時の優先順位付け）を決めて、
その上で改めて事前登録し直すこと。

### 4-5. 第2レジームでの再検証（未着手）

2025年以降は四半期報告書の廃止で母数が薄く（2,000件台）、事前登録 §4 で
合否対象外としている。制度変更後のデータが積み上がった時点で、
**第2レジーム単独での再検証**を行うこと。

## 5. v2 バックテストの結果（2026-09-02）

設計の正本: `docs/backtest_acceptance_criteria.md` の「v2 事前登録」。
v1 の診断（4-3 / 4-4）を受けた設計修正を、**実行前に**事前登録して1回だけ回した。

修正は2点のみ:

1. **ポジション枠**（測定装置の修正）: 同時保有10枠のハード制約。枠が埋まれば
   新規シグナルはスキップ。同日の候補が空き枠を超える場合は score 降順で採用。
   資産曲線は実行可能な建玉のみで計算。
2. **市場フィルター**（設計の修正）: TOPIX が200日移動平均を下回る間は新規
   エントリー停止。エグジット判定は不変。

### 5-1. 形式的判定: 合格

主セル T-15 × T+2、コスト往復0.4%控除後。

| # | 項目 | 基準 | v1 | v2 | |
|---|---|---|---|---|---|
| 1 | トレード数 | ≥ 300 | 1,743 | **334** | 合 |
| 2 | 期待値（純） | > 0 | +2.09% | **+1.47%** | 合 |
| 3 | TOPIX超過 | > 0 | +0.35% | **+0.21%** | 合 |
| 4 | 最大DD | ≥ -15% | -32.30% | **-13.84%** | 合 |
| 5 | 利益集中度 | < 30% | 7.02% | **21.80%** | 合 |

勝率 51.5%、最終NAV 1.574。**5項目すべて達成し、頑健性チェック2本も通過**
（グリッドの期待値プラス3/3、±3シフトの期待値プラス3/3・勝率変動1.5pt）。

建玉が 1,743 → 334 に減ったのは、**枠満杯によるスキップ 1,293件**と
フィルターによるスキップ 116件。v1 が実行不能な建玉を数えていたことが
そのまま差になっている。

フィルターの作動は32日 / 116イベント。2024年8月の急落局面と
2025年4月の下落局面で正しく停止している。

### 5-2. 質的評価: 主セル1点でのみ成立する脆弱な合格

**形式的には合格だが、その周辺は基準を割っている。**

- **±3シフトで MDD が基準外**: -3 で **-19.41%**、+3 で **-24.06%**。
  合格した -13.84% は**シフト3本のうちたまたま最良の1本**である。
- **エントリー感応度でも MDD が基準外**: T-10 が **-16.30%**、
  T-5 が **-24.71%**。基準を満たすのは主セル T-15 のみ。
- **合格ラインぎりぎりの項目が複数**: トレード数 334（要件300、余裕34件）、
  TOPIX超過 +0.21%（コスト0.4%の見積り誤差1回で消える水準）、
  MDD -13.84%（基準まで1.2pt）。

**基準設計の穴を認める**: 事前登録の頑健性チェックは**期待値と勝率しか
対象にしていなかった**。MDD を頑健性の対象に含めていれば、この合格は
「頑健性チェック不通過」として扱われていた。基準の側の設計ミスであり、
結果を見てから気づいた以上、v2 の判定自体は動かさない。

### 5-3. 結論: 実弾投入は行わない

**ペーパートレードによる前向き検証に移行する。** 設計書は
`docs/paper_trading_design.md`。

インサンプルでの再チューニングは v2-4 のとおり行わない。次の判断材料は
**アウトオブサンプルの実績**であって、同じ5年のデータの切り直しではない。

### 5-4. 将来の事前登録への教訓

**頑健性チェックは期待値・勝率だけでなく MDD も対象にする。** v3 以降の
事前登録で必ず反映すること。期待値と勝率が安定していても、資産曲線の
谷の深さが条件次第で倍近く動くなら、それは頑健とは呼べない。

## 6. v3 検討課題（v2運用中は変更しない）

### 6-1. 単一シグナル銘柄の高スコア化

`score_ticker` の合成スコアは **available なシグナルの平均**という仕様。
したがって **8本中1本しか available でない銘柄も、その1本の点数がそのまま
合成スコアになる**。

実例（2026-09-02 のペーパートレード初回凍結、銘柄 1418）:

```
S1 (0.0, available=False)   S5 (0.0, False)
S2 (0.7, available=True)    S6 (0.0, False)
S3 (0.0, False)             S7 (0.0, False)
S4 (0.0, False)             S8 (0.0, False)
→ evidence_score = 0.700   （S2 単独）
```

閾値0.10に対して0.700は上位。**8本の証拠が揃った銘柄と、1本しか無い銘柄が
同じ土俵で順位付けされる。** 10枠の優先採用は score 降順なので、
証拠の薄い銘柄が枠を取る可能性がある。

**v3の検討候補**: 「スコア算出に最低N本の available を要求する」
「available 本数で重み付けする」「available 本数を枠の優先順位の
第2キーにする」など。

**v2運用中は変更しない。** 事前登録済みの仕様であり、走っている検証の
途中で判定関数を変えたら前向き検証の意味が消える
（`backtest_acceptance_criteria.md` v2-4 / `paper_trading_design.md` §4-1）。

### 6-2. 発表日の確定ソースが存在しない（実測で確定）

2026-09-02 に3経路すべて実測し、**確定予定日のソースは存在しない**と確定。

| 経路 | 実測 | カバレッジ |
|---|---|---|
| J-Quants `/equities/earnings-calendar` | 1件のみ。しかも過去日(2026-08-17) | **0.1%** |
| TDnet 適時開示（全件を直接取得） | 5営業日 975件中 **0件** | **0.00%** |
| 決算短信XBRL内の次回予定日 | `tse-ed-t:FilingDate`(空) のみ。該当要素なし | — |

TDnet はアーカイバがタイトル正規表現で3種別に絞っているため「絞り込みで
捨てているだけでは」と疑い、**全開示975件を直接取得して確認した上でのゼロ**。
企業は次回発表予定日を独立した適時開示としては出していない。

→ **前年同期推定（別枠 Module A）を主エンジンとして固定。** 格下げなし。
推定誤差は ±3営業日シフトの感度分析で許容済み（1-2b）。

**副産物**: ペーパートレードの `calendar_reconciliation` が推定と実績の
差を蓄積するので、**1-2b で測定不能だった代理日の誤差を、前向きデータで
実測できるようになる**。過去は測れなかったが、これからは測れる。

## 7. 前向き期とバックテスト期の土俵が違う（2026-09-02 実測で確定）

### 7-1. 前向き期のポートフォリオは証拠の薄い銘柄で構成される

**これは欠陥ではなく現実の反映であり、v2 の解釈に必ず添えること。**

2026-09-14 週の初回凍結を実測すると:

```
候補 61件の available シグナル本数
  0本: 35件 / 1本: 26件 / 2本以上: 0件
v2 が entry した13件: すべて available=1本
```

8本のシグナルのうち **最大1本しか動いていない**。合成スコアは available の
平均なので、13件はすべて「1本の点数がそのまま合成スコアになった」もの。

**原因（構造的）**: スコアラーは5四半期分のPITデータを要求する。四半期報告書の
廃止（2024-04-01以後開始の四半期）で Q2・Q4 が半期粒度（span_q=2）になり、
投影層が「四半期として渡せない」ものとして落とすため、2025年以降は
**真の四半期チェーンが構築できない**。

**したがって**: v2 バックテストが +1.47% を出した 2022〜2024年は四半期報告書が
存在した期間であり、**前向き検証が走っている現在とは土俵が違う**。
両者を単純比較してはいけない。

**解釈の方針（2026-09-02 決定）**: v2 の前向き検証は継続する。ただし
**凍結レコードの available 本数で層別して解釈する**。「証拠1本の
ポートフォリオがどう振る舞うか」は、それ自体が制度変更後の現実である。

### 7-2. B3（4分岐エグジットの設計検証）は判定不能

同じ根で、`forecast()` が要求する「前年同四半期の単独値」が無い。

```
v2と同じ建玉334件 → 評価できたのは 7件(2.1%)
  前年同四半期のデータなし          275件
  データ不足orカレンダー未登録       19件
  実績が取れず                      33件
```

参考値（7件・統計的意味なし）: 固定T+2 −0.39% / 4分岐 −0.09% / 差 +0.30pt。
分岐は EXIT 5件・STOP_LOSS 2件で、**TP_ALL と TP50_TRAIL が未発火**。
4分岐のうち2分岐が一度も検証されていない。

**事前の取り決めどおり1回のみで打ち切り、パラメータは変更しない。**
再検証は span-matched YoY モード（`docs/span_matched_design.md`）の完成後。

### 7-3. 例外を「利用不可」に潰す設計が繰り返し原因究明を妨げている

2026-09-02 の1日で**同じ構造の失敗を3回**踏んだ。

| 症状 | 真因 |
|---|---|
| 候補1,773件が全部 skip_score | `row_factory` 未設定 → 全スコアラーが TypeError → `available=False` |
| B3 が334件すべて「データ不足」 | 投影DBに `evidence_events` が無い → OperationalError → 握り潰し |
| 週次バッチが SyntaxError | `python -c` への複数行引数が壊れる |

上2件は同一構造。別枠 `score_ticker` と呼び出し側の `try/except` が例外を
「利用不可」に変換するため、**配線ミスとデータ不足が完全に同じ見た目になる**。
午前に踏んだ `xbrl_parser` の stderr 握り潰しとも同じ構造で、
**このプロジェクトで最も再発している失敗**。

対策として (a) 例外率が5割を超えたら停止するガード、(b) 例外とデータ不足の
別カウント、を入れた。ただし根本は「例外を握り潰す設計」であり、別枠は
変更禁止なので**呼び出し側で毎回ガードを書く**しかない。新しい呼び出しを
書くときは必ずこれを入れること。

## 9. S12（定性文言diff）の初回実測で見つかった構造的な偏り

`config/s12_dictionary.yaml` の重みは**事前登録の初期値**。以下はいずれも
**実測された事実の記録であって、変更の決定ではない**。

> **変更する場合は新規事前登録とし、フォワード適用のみ。**
> 同一データ（3,810ペア／実際に構築できた 7,488組）を見てから重みを
> 動かすことは禁止。これを破ると、S12 は「過去に当てはまるよう調整した
> 辞書」になり、前向きの意味が消える。

### 9-1. Tier C が支配的（設計意図と逆）

初回全件評価（2026-09-02、available 4,125件）の内訳:

| 層 | ヒット数 | スコア合計 |
|---|---:|---:|
| Tier A 硬い事実 | 495 | **-3.54** |
| Tier B セグメント方向 | 1,159 | +1.70 |
| **Tier C 語彙diff** | **3,508 (68%)** | **+30.66** |

設計は Tier A（受注・値上げ・稼働・減損など金額に直結する事実）を主軸に
置き、Tier C は補助のつもりだった。実際は **合計スコアの大半が Tier C で
決まっている**。「硬い事実」より「評価語が前年から現れたか」で点が付く
状態で、意図と逆。

原因は重み(0.03)ではなくヒット数の桁が違うこと。Tier A は該当する事実が
起きた時だけ出るが、Tier C は評価語が1つ入れ替わるだけで出る。

### 9-2. Tier C の正の非対称（市場環境バイアス仮説）

Tier C の上位語:

```
appeared:回復 527 / 改善 511 / 堅調 392 / 好調 281 / 拡大 263
appeared:低迷 244 / 減速 241 / 下振れ 205
```

positive 側が negative 側を明確に上回る。**「前年に無く当期に現れた語」を
数える設計上、景気回復局面では positive が構造的に増える**。個社の変化では
なく市場環境を拾っている可能性がある。

これが正しければ、S12 は**銘柄選択のシグナルではなく市場環境の代理変数**に
なってしまう。検証するなら「同一四半期の全銘柄で Tier C の平均を取り、
それを控除した残差を使う」等が候補だが、**これも新規事前登録が要る**。

### 9-3. 併せて記録: dedup は実データで作動した

TDnet の業績予想修正が既にある銘柄で `forecast_revision` が 0 点になった
実績が1件。二重計上を防ぐ機構は動いている。根拠文は消さず点だけ落とす
実装なので、後から「なぜ0点か」を追える。

### 9-4. 節見出しの取りこぼし修正（重みの調整ではない）

**これは §8 の区別でいう「値を正しく適用できていない実装の修正」であり、
重みの再調整ではない。** 辞書の重みは1つも触っていない。

初回実測で available 55%（欠損 3,292 件のほぼ全部が「経営成績の節が
見つからない」）。原因は見出しの表記が書類種別で違うことだった。

| 種別 | 構造 |
|---|---|
| 四半期報告書(140) | 「(1) 経営成績の分析」／「a.経営成績の状況」／「①経営成績の状況」 |
| 半期報告書(160) | 「２【経営者による財政状態、経営成績及びキャッシュ・フローの状況の分析】→ (1) 財政状態及び経営成績の状況 → (経営成績の状況)」 |
| 有価証券報告書(120) | 「４【経営者による…分析】」（§1 は経営方針なので飛ばす必要あり） |

修正は2段階。**1段目で新たな誤りを作り、2段目で直した**ので両方記録する。

1. **見出しパターンの拡張**（55% → 60%）。160 の入れ子構造と
   「財政状態及び経営成績の状況」形式を追加。
2. **行頭アンカーと最長本文の採用**。1段目では「最も内側（最後に出る）
   見出し」を採る実装にしたが、これが
   **「『経営者による財政状態、経営成績…の分析』中の会計上の見積り」
   のような参照文を見出しと誤認**し、本文が 30字しか取れないケースを
   作った（9252 / 7279）。行頭にあるものだけを見出しとみなし、
   候補の中で**本文が最も長く取れるもの**を採るよう修正。

   ```
   修正前: 9252 → 30字（参照文から開始）
   修正後: 9252 → 1,180字（「①経営成績の状況」から開始）
           7279 → 3,487字 / 5757 → 1,407字
   ```

**教訓**: 「内側の見出しほど正確」は多くの場合正しいが、**同じ語が本文中の
参照として現れる文書では逆に働く**。位置ではなく「行頭にあるか」という
構造的な手がかりで判定すべきだった。

## 10. 投影層が別枠の語彙で喋っていなかった（2026-09-02・修正済み）

投影層 `balance_sheet_items` は**本体の item 名のまま**書かれていた。
別枠は自分の item_key で引く。写像表
（`screener/config/earnings_screener_mapping.yaml`）は最初から

結果、**別枠が名前で引けない項目のスコアラーは全銘柄で available=False**
だった。テーブルは存在し行もあるので、「データが無い」ようにしか見えない。

| 別枠の item_key | 本体の item | 修正前 | 修正後の available 率 (n=400) |
|---|---|---|---|
| accounts_receivable | trade_receivables | 引けない | S1 **0% → 34.5%** |
| machinery | machinery_and_equipment | 引けない | S3 **0% → 31.5%** |
| inventory | inventories_total | 引けない | S6 **0% → 1.5%** |
| contract_liabilities | (同名) | 引けた | S2 14.8% |

**これまでのバックテスト v1/v2、ペーパートレード、シャドウ A/B/C は

## 16. 原文リンクの健全性検査（2026-09-02・実装済み）

製品定義が「スクリーニング自動化・最終判断は人間」である以上、
**原文リンクはスコアと同格の成果物**である。飛べなければスコアは検証できない。
`weekly_screen` に検査を組み込んだ。

- **形式検証（既定・毎回）**: EDINET は
  `https://disclosure2.edinet-fsa.go.jp/WZEK0040.aspx?S+7英数`、
  TDnet は `.../inbs/*.pdf`。空・前後空白・形式ちがいを行ごとに報告する。
- **生存確認（`--verify-links` 指定時のみ）**: 実際に取得し、HTTP 200 と
  **提出者名がページ本文にあること**を確認する。

### 照合キーに証券コードを使ってはいけない

最初は「本文に銘柄コードが含まれるか」で照合し、**3070 を誤検知した**。
EDINET のページはコードを全角（６３３６）や5桁（63360）で出すことがあり、
**訂正報告書では一切載らない**。3070 の訂正有報がまさにそれで、
ページは正しい書類（本文に「ジェリービーンズ」あり）なのに不合格になった。

照合は `filings.company_name`（提出者名）で行う。書類の先頭に必ず出るため。
コードは補助的な手がかりとしてのみ見る。

**教訓**: 識別子の見た目が表示側で変わる媒体では、識別子そのものより
**名前**のほうが安定した照合キーになることがある。

### 2026-09-02 の実測

全9行・形式 edinet 9件で問題なし。生存確認も9件すべて 200 かつ提出者名一致。
6336 石井表記 `?S100Y0EE` は完全な形式で、取得すると
title「提出書類内容照会画面（提出本文書）」・本文に「石井表記」を含む。

### 残る弱点（未着手）

`_latest_doc` は**銘柄の最新開示**に飛ばすので、スコアの根拠になった期の
書類とは限らない。今回の9件はたまたま一致していた（半期単独値は
有報から引き算で作るため）が、一致は保証されていない。
「根拠の期の書類に飛ぶ」に変えるべきだが、スコアが複数期を使う
（S4 は1年ぶんを積む）ので単一リンクに落とせない。設計が要る。

## 17. 原文リンクを根拠期の書類に変更（2026-09-02・実装済み）

§16 で残していた弱点（`_latest_doc` が**銘柄の最新開示**に飛ばすので、
スコアの根拠になった期の書類とは限らない）を解消した。

### 実装

1. 投影層 `filings` に **`doc_id` 列**を追加。(code, period, q_no) を初めて
   開示した書類の doc_id を本体から写す。35,002 行すべてに入った
   （edinet 26,728 / tdnet 8,274）。
2. `span_scorers` の各結果に `doc_id` / `doc_date` / `doc_source` /
   `doc_path` / `period_note` を持たせる。S12 が `filing_id` を直に持つのと
   同じ形（シグナル→根拠書類）を S1/S2/S4/S5 にも与えた。
3. **複数期を積むスコア（S4 の1年ぶん、S5 の期首累計）は最新の根拠期に
   リンクし、含まれる期を `period_note` に明記する。** 1本のリンクで
   複数期は表せない以上、含まれる期を書かないと嘘になる。
4. 週次レポートは `原文(根拠期)` と表示し、シグナルごとにリンクが分かれる
   場合は「シグナル別」行を出す。CSV に
   `doc_kind` / `doc_period` / `doc_note` / `evidence_docs` を追加。

### 検証（`--verify-doc-periods`）

**投影層を経由せずに照合する。** 投影層の filings でリンクを作っている
以上、同じ表で照合しても「作った通りに作れている」しか言えない。
本体の事実表 `financials_cum` に (period, q_no) の行が実在するかを見る。

| 出力 | 一致 | 不一致 | 根拠期を持たない行 |
|---|---|---|---|
| 週次スクリーン（9銘柄） | **15** | **0** | 2 |
| カレンダー全件（28銘柄） | **44** | **0** | 5 |

「根拠期を持たない行」は別枠の位置ベース比較しか使えなかった銘柄。
期が特定できないので**リンクを作らず、最新開示に落ちる**ことを
`doc_kind` 列に明示する（黙って別の書類を「原文」と称さない）。

### 変更で見えるようになったこと

リンクが根拠期を指すようになった結果、**根拠が古い銘柄が可視化された**。

- 3565 アセンテック: S1/S2 の根拠期は FY2025-Q2（開示 2024-09-11）。
  最新データは FY2026-Q2(span=2) だが、前年 H1 が span=2 の行として
  存在せず（FY2025 は Q1/Q2 が span=1）、同じ span の前年が見つからない。
- 3070 ジェリービーンズG: 同様に FY2025-Q2（開示 2024-09-12）。
  従来は最新開示（2026-07-28 の訂正有報）に飛ばしていたので、
  **根拠の古さがリンクからは見えなかった。**

いずれも `MAX_STALE_Q=4` の範囲内なので available のまま。

### 【未着手】前年の同一 span を集約して作る

3565 の例は「前年 H1 は Q1+Q2 を足せば作れる」ケースである。
`find_yoy_peer` は**既存の行しか探さない**ので取り逃がしている。
足して作れば当期 FY2026-Q2(span=2) と比較でき、根拠が2年新しくなる。
ただし「集約して作った前年」は開示された値ではないので、

## 19. シグナル鮮度（stale）の実測（2026-09-02・表示のみ）

### 症例

3565 アセンテックの契約負債シグナル（S2）は根拠期 **FY2025-Q2**、

別の粒度でしか無いと当期は組めず、**組める最後の期まで遡る**。遡ること

`screener/report/stale_audit.py`。当時の as_of で PIT 再計算するので、

| forecast_snapshots（ペーパー） | 41 | **9** | **22.0%** |
| shadow_snapshots（シャドウA/B/C） | 39 | **9** | **23.1%** |

## 25. 【タスクE】前年H1の合成（2026-09-02・実装）

### stale の真因は取り込みではなかった

### 実装で見つかった別の欠陥 —— 行の存在と値の存在は別物

- 区間を隙間なく覆う span=1 の行だけを使う。1本でも欠けたら**作らない**

- 項目ごとに独立に合成。欠けた項目は None（0 で埋めない）

## 26. 【タスクD】stale lag の定義（2026-09-02・明文化）

    lag = latest の期インデックス − basis の期インデックス（単位: 四半期）
    期インデックス = fy * 4 + (q - 1)

    basis=FY2025-Q2, latest=FY2026-Q2 → 4
    basis=FY2025-Q2, latest=FY2027-Q1 → **7**

span の長さは見ない。「どれだけ前の期の話か」であって「何ヶ月ぶんの期か」
ではない。当初 fixture の「basis=FY2025-Q2 / latest=FY2027-Q1 → lag=4」は
算術誤りで、正しくは 7。テストで固定した。

なお当DBに 3565 の FY2027-Q1 は存在しない（§24-b）。実データでの
latest は FY2026-Q2 なので、実測の lag は 4 になる。

（「予想FY ≤ 最新実績FY なら履歴であって予想ではない」）で採用を**拒否し理由を記録**したため
実害は出ていない。ただしラベルが正しければ使えたはずの会社予想であり、取りこぼしている。

- 影響範囲の調査が必要: 他に何社が同じ経路でずれているか（タイトル由来の採番を
  DEI の会計期間と突合すれば機械的に検出できるはず）。
- 対処案: `fy` の決定を短信タイトルではなく XBRL の DEI（`CurrentFiscalYearEndDate` 等）に寄せる。

### C-P2-2. 米国基準の決算短信から業績予想が抽出できない（4901 富士フイルム / 7751 キヤノン）

両社とも短信XBRL はアーカイブ済み（`filings.xbrl_ok = 1`）で解析も走っている
（`financials_cum` に行がある）が、`guidance` の行が **0件**。
米国基準短信の予想ファクトが screener 側のタグマッピングに載っていない。

- 対処案: `screener/config/*_mapping.yaml` に米国基準（`tse-*-usedjp*`）の
  Forecast 系タグを追加する。まず2社の Summary inline-XBRL のタグ名を列挙して現物合わせする。

### C-P2-3. 追補6 §X の裁定が再生成で必ず失われる

`batch/demote_dcf_leg.py` は完成したワークブックを後から編集する設計のため、
`generate_dcf.py` による再生成は降格を**必ず取り消す**（6857 アドバンテストの Target が
4,288 → 8,021 に戻ったのが実例。評価の変化ではなく裁定の不在）。
現状は `batch/apply_arbitration.py` を再生成後に走らせる運用で塞いでいる。

- 対処案（要検討）: 乖離の判定と脚の降格をテンプレート側（`dcf_comps_template.py`）に
  内蔵し、生成時に決着させる。ただし §X は Peer の観測倍率バンドを使うため
  comps の統計が確定した後でなければ判定できず、生成順序の設計が必要。
- 対処しないなら、**運用手順書に「再生成 → 再裁定」を明記する**こと。

### C-P2-4. EDINET の IFRS 営業利益タグが 7741 HOYA で抽出できない

キュー再スクリーン（`batch/phase2_rescreen.json`）で、7741 は EDINET から
revenue 947,749 / 純利益 253,085 / D&A 58,218 は取れるが
**営業利益・COGS・SGA が取れない**。v1 の報告は「yfinance の誤マッピング」だったが、
一次ソース側にも同じ穴があることが判明した（原因の所在が特定された、という前進）。

- 対処案: docID S100Y90T（FY2026/3）の XBRL で `OperatingProfitLossIFRS` 系タグの
  実際の要素名を確認し、`scripts/edinet_parser.py` の候補リストに追加する。

### C-P2-5. TOPIX 回帰βの相関が低い9銘柄
