# 傾き検出スクリーナー 仕様書 v1(2026-08-29)

ClaudeCode実装用。リポジトリ: ryosuke-japanese-equity-research 内に `screener/` パッケージとして構築。
既存規約を継承: 銘柄コード入りスクリプト禁止(check_script_naming.py)、推定・設計判断のログ記録、サイレントフォールバック禁止。

## 0. 目的と思想

- **目的**: 先生(キオ君)が目視でやる「短信全読み」を自動化し、業績の傾きが変わる**証拠が数字に出た瞬間**を、市場が織り込む前に検出して週次上位20社に絞る
- **思想**: これは予言機ではなく**確認の高速化装置**。「証拠確認後に入る」という投資の型の中で、確認の速さだけを競う。BSに積まれた売上の在庫(原材料・仕掛・建設仮勘定・契約負債・前受金)がPLに変換される直前・直後を捉える
- **非目標**: 買い推奨は出さない。出力は「証拠と根拠のリスト」であり、判断は逆算DCF(既存パイプライン)と人間が行う。「約束」(MOU・計画・目標)は検出対象external、「証拠」(計上済みの数字)のみをシグナルとする

## 2. 取得層

### 2-1. TDnet日次アーカイバ(最優先・P0。APIキー不要、今日から動かせる)
- TDnetの適時開示一覧(日次)を毎営業日取得し、PDF+XBRL(短信)を `data/raw/tdnet/YYYYMMDD/` に保存、メタデータをDBへ
- **公式サイトの保持は約1ヶ月のみ。蓄積を1日でも早く始めることが資産になる**(遡及不能)
- 対象書類: 決算短信(四半期含む)・業績予想修正・配当予想修正。全上場でも1日数百件、全部保存してよい
- 実行: cron/タスクスケジューラで平日夕方1回+リトライ。取得失敗日はDBに欠損記録(黙って飛ばさない)

### 2-2. EDINET一括取得(P1。APIキー必要)
- EDINET API v2で有価証券報告書・半期報告書のXBRLを一括取得。初期ロードはユニバース約1,900社×直近3年(一晩〜二晩、レート制限に注意して間隔を空ける)
- 用途: 実績時系列の土台、セグメント注記、自己株、詳細BS科目。※四半期報告書制度は廃止済みのため、四半期のBS/PLは**短信XBRL(TDnet)が主源泉**。EDINETは年次・半期の深掘り用と割り切る

### 2-3. J-Quantsユニバース(P1。無料プラン)
- 上場銘柄一覧・市場区分・株価・売買代金・**時価総額**を取得。無料プランの12週遅延はユニバース条件(規模・流動性)には許容
- SBIスクリーナーCSVは月1手動取り込みの補助のみ(自動巡回しない。既決定)

#### API V2 移行(2026-08-31 実施)
V1 は **2026-06-01 に提供終了**。全エンドポイントが403を返していた原因はこれで、資格情報の問題ではなかった。V2 はダッシュボード発行のAPIキーを `x-api-key` ヘッダーで送る(`.env` の `JQUANTS_API_KEY`)。`Authorization` ヘッダーとの同時送信は不可。トークンの二段認証・自動更新・キャッシュは全て不要になった。

| 項目 | V1 | V2 |
|---|---|---|
| ベースURL | `https://api.jquants.com/v1` | `https://api.jquants.com/v2` |
| 認証 | `Authorization: Bearer <idToken>`(mail+password → refreshToken → idToken) | `x-api-key: <APIキー>` |
| 上場一覧 | `/listed/info` | `/equities/master` |
| 日次四本値 | `/prices/daily_quotes` | `/equities/bars/daily` |
| レスポンス本体 | エンドポイント毎に別名の配列 | `data` 配列に統一 |
| 銘柄名 | `CompanyName` | `CoName` |
| 33業種/17業種 | `Sector33CodeName` / `Sector17CodeName` | `S33Nm` / `S17Nm` |
| 市場区分 | `MarketCodeName`(市場+商品種別の合成) | `MktNm`(市場のみ) + `ProdCat`(商品種別) |
| 四本値 | `Close` / `Volume` / `TurnoverValue` | `C` / `Vo` / `Va` |
| 時価総額 | **取得不可** | **`MktCap`(百万円)が日次バーに追加** |
| レート制限 | 実質無制限 | **分あたり**: Free 5 / Light 60 / Standard 120 / Premium 500 req/min |

**運用上の含意**

1. **時価総額がAPIから取れるようになった**。V1 では `mktcap` が常に NULL で、全銘柄が `exclude_reason='時価総額未取得'` のまま滞留し、ユニバース条件の規模判定が**一度も実行できていなかった**。V2 で規模・流動性の両方が判定可能になり、ユニバースが初めて確定した。
2. **リクエストが希少資源になった**。無料プランは5 req/min = 実質「1営業日ぶんの株価取得に1リクエスト」。`--rpm` でプランを指定し、間隔は `60/rpm × 1.3`(+30%マージン)で算出する。公称値ちょうどや+10%では1分窓の境界で必ず429になり、429ごとに65秒失って実効速度がかえって落ちる(実測確認済み)。429を検知したら間隔を1.3倍する自動減速を入れてある。
3. **`--price-days` は25で足りる**。ADVの窓は `liquidity.adv_window_days`(20日)なので、40日ぶん取っても新しい20日しか使わない。25営業日あれば休場日を挟んでも20日を埋められる。
4. **商品種別の除外は `ProdCat` 由来**。V2 の `MktNm` は「プライム」等の純粋な市場名で、REIT/ETF/優先出資証券の別は `ProdCat` に分離された。`jquants_universe.PRODUCT_CATEGORY` が商品種別名を市場名に併記して復元し、`by_market_name` での除外を維持している。市場名だけを見る実装にすると **REIT/ETFが黙ってユニバースに混入する**。
5. **市場区分の照合は大文字化して行う**。DB には `TOKYO PRO MARKET`(V2 / JPX)と `PRO Market`(過去取込)が混在する。素の部分一致では後者を取りこぼし、「除外」ではなく「未判定」に化ける。

### ユニバース条件(config/universe_rules.yaml)
- 時価総額50〜**1,000億円**/20日平均売買代金3,000万円以上(スパイダープラスの教訓の機械化)/銀行・保険・REITを除外

**変更履歴**

| 日付 | 変更 | 理由 |
|---|---|---|
| (初版) | 時価総額 50〜600億円 | 先生の型③ |
| 2026-08-31 | 時価総額上限 600億 → **1,000億** | **ユーザー戦略判断により上限拡大。準小型のテーマ化銘柄まで対象に含めるため。** 下限50億・ADV20 3,000万円は据え置き |

この拡大は**投資対象としての戦略判断**であり、§6 の検証8銘柄をユニバースに入れるための変更ではない。§6 の原則は維持する —— 検証で調整するのは S1〜S8 の重みであってユニバース条件ではなく、8銘柄が入るようにレンジを動かしてはいけない。実際、上限1,000億でも 285A キオクシア(42兆)/3110 日東紡(7,639億)/3905 データセクション(1,564億)/6855 日本電子材料(1,132億)はユニバース外のままである。

## 3. 抽出層

### 3-1. XBRL科目マッピング(config/account_mapping.yaml)
短信XBRL(tse-ed-t/jppfs)タグ→内部項目。最低限のセット:
売上高/売上原価/売上総利益/販管費/営業利益/経常利益/親会社純利益/通期会社予想(売上・営業利益)/現金及び預金/売掛金・受取手形・契約資産/商品及び製品/仕掛品/原材料及び貯蔵品/棚卸資産計/**建設仮勘定**/機械及び装置/**契約負債**/**前受金**/短期借入金/長期借入金/自己株式/純資産。
- 科目名の会社間ゆらぎ(例:「原材料及び貯蔵品」vs「原材料」)は別名テーブルで吸収。マッピング不能タグは unknown として記録し、頻度上位を定期レビュー(黙って捨てない)

### 3-2. 四半期単独値ビルダー(quarterly_builder.py)——本システムの心臓
- 短信は累計表示のため、**Q単独値=当期累計−前四半期累計**を全項目で機械生成
- 3441で実証済み: 9ヶ月累計の粗利率24.2%の裏で、Q3単独は21.9%と既に低下していた。**累計は平均で嘘をつく。単独値だけが傾きを語る**
- 決算期変更・遡及修正・連結範囲変更はフラグを立てて単独値を無効化(誤検出防止)

### 3-3. 定性テキスト(pdf_text.py、P2後半)
- 短信の「経営成績に関する説明」「今後の見通し」を抽出・保存。前四半期との文言diffを生成

## 4. 指標層(signals/signal_defs.py)

各シグナルは (値, 発火bool, 根拠文字列) を返す。閾値はconfigで外出し。

| ID | シグナル | 定義 | 備考 |
|---|---|---|---|
| S1 | Q単独粗利率の傾き | Q単独GM% − 前Q単独GM%(qoq)および前年同Q比(yoy)。+1.5pt以上で発火 | 3441型の主砲。低下側は逆シグナルとして減点。**セグメント軸では営業利益率で代替**(下記) |
| S2 | 在庫の価格/数量分解 | Δ棚卸% を ΔCOGS%(価格プロキシ)と回転日数変化(数量)に分解 | **在庫増は両義的**。数量要因の増加×売上加速=仕込み(加点)、×売上減速=滞留(減点) |
| S3 | 建設仮勘定 | 建仮の急増(前Q比+30%以上)=稼働前投資。建仮減×機械装置増=**振替検出(稼働開始の証拠)** | 振替はS3b として別発火(3905のQ2チェックと同型) |
| S4 | 契約負債・前受金 | 前Q比・前年比の増加率。売上成長率を上回る増加で発火 | 顧客コミットの現金証拠(3905の前受金マーカーと同型) |
| S5 | 転換・進捗率異常 | ①営業損益の赤字→黒字転換(Q単独) ②累計進捗率が通期予想を四半期数比で大幅超過(例: Q3時点で100%超)=**死んだガイダンス検出** | 3441の進捗113%型。上方修正の先回り |
| S6 | 文言差分 | 見通し文の前期比diffに増額系語彙(上方・増額・過去最高・前倒し)出現、慎重系語彙の消滅 | P2後半。最初はルールベースで十分 |
| S7 | 修正方向の転換 | 業績予想修正の履歴が 下方→据置→上方 と転じた初回 | TDnetアーカイブから |
| S8 | 売上債権の質(逆) | 売上債権増加率が売上増加率を大幅超過(粉飾・押し込みの疑い)で減点 | 掲示板ノイズでなく数字で疑う |

**S1 のセグメント別適用について(2026-08-31 追記)**

セグメント別の**粗利率は多くの会社で算出できない**。XBRL のセグメント注記に COGS が無いため —— 実測で取れるのは売上(`RevenuesFromExternalCustomers`)、セグメント利益、減価償却費、資本的支出まで。したがって **S1 をセグメント軸に適用する場合は「セグメント別営業利益率」で代替する**。全社レベルの S1 は従来どおり粗利率で計算する(3441 の主砲はここ)。

セグメント次元の保持方法・区分変更時の無効化ガードは `docs/segment_dimension_design.md` を正とする。

### スコアリング(scorer.py)
- 合成スコア = Σ(重み×発火)。初期重みはconfig/signal_weights.yamlに仮置きし、**検証(§6)の結果で調整してから本運用**
- 出力は週次上位20社+各社の発火シグナル・根拠数値・原文該当箇所

## 6. 検証プラン(実装P3。本運用の前提条件)

**検証8銘柄**: 285A キオクシア/2962 テクニスコ/3110 日東紡/278A テラドローン/3905 データセクション/6217 津田駒/4192 スパイダープラス/「電子材料」(先生リスト表記。日本電子材料6855と推定、**要確認**)
- 各銘柄で「傾きが株価に現れた四半期」を人手で特定し、その**1〜2四半期前**の短信でS1〜S8が発火したかを判定
- 期待する結果の例: テクニスコ=傾き前にS1/S2発火していれば合格。津田駒=S8や継続企業注記でスコアが抑制されれば合格(見送り判定の再現)。テラドローン=発火しない(物語先行・数字に証拠なし)ことが正解——**発火しないべき銘柄で発火しないことも検証項目**
- 検証結果を docs/ にレポート化し、重みを調整してから週次運用開始

**検証8銘柄はユニバースの部分集合ではない**(2026-08-31 確認)。ユニバース条件を適用すると8銘柄中3銘柄(2962 テクニスコ/6217 津田駒/4192 スパイダープラス)しか残らず、残り5銘柄は全て**時価総額上限(600億円)超過**で除外される — 285A キオクシア 42兆6,909億/3110 日東紡 7,639億/3905 データセクション 1,564億/6855 日本電子材料 1,132億/278A テラドローン 798億。8銘柄は「傾きの出方が既知である」という理由で選ばれた**シグナル検証用の教師データ**であって、ユニバース条件で選ばれた銘柄ではない。したがって:
- EDINET/TDnet の取得対象は「ユニバース ∪ 検証8銘柄」とする。ユニバースだけを対象にすると検証データが5銘柄ぶん欠ける
- 検証で調整するのはS1〜S8の重みであって、ユニバース条件ではない。8銘柄が入るようにレンジを広げてはいけない(型③の定義が壊れる)

## 8. 運用ルール

- シグナルは「証拠」の検出器。MOU・受注計画・目標値など「約束」は検出根拠に使わない(メタデータとして保存はする)
- 発火銘柄の次工程は既存パイプライン: 逆算DCFで織り込みを測ってから判断(スクリーナー→DCFの接続がフルサイクル)
- 週次30分の人間レビューを前提とし、レポートは根拠の原文にリンクする形で出す(ブラックボックス化しない)
