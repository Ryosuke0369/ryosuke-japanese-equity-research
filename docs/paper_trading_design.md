# ペーパートレード設計書（前向き検証）

**状態: 承認済み（2026-09-02）。実装中。**
作成 2026-09-02。

## 0. なぜこれをやるのか

v2 バックテストは形式的には合格したが、**主セル1点でのみ成立する脆弱な合格**
だった（`calibration_backlog.md` 5-2）。±3シフトで MDD が -19.4% / -24.1%、
エントリーを T-10 / T-5 に振ると MDD が基準外になる。

インサンプルで再チューニングしても答えは出ない（同じ5年を切り直すだけ）。
必要なのは**まだ見ていないデータでの実績**である。実弾を入れずにそれを得る
のがペーパートレードの目的。

**この検証で問うのは「儲かるか」ではなく、「バックテストで見た数字が
前向きにも再現するか」**。再現しなければ、v2 の合格は過去への適合だった
ということになる。

## 1. 週次バッチの本番運用形

毎週月曜（祝日なら翌営業日）の朝に、以下を1本のジョブとして流す。

```
run_paper_weekly.ps1
  ├ 1. カレンダー再構築     決算発表予定の更新（EDINET索引 + TDnet）
  ├ 2. 候補抽出             T-15 に該当する銘柄を洗い出す
  ├ 3. スコアリング         score_ticker(as_of=当日) で PIT 評価
  ├ 4. 市場フィルター判定    TOPIX 200日移動平均（前日まで）
  ├ 5. 建玉シミュレーション  10枠制約・score降順で採用可否を決める
  ├ 6. エグジット判定       保有中ポジションの4分岐ルール
  └ 7. レポート出力         週次サマリ + 仮想トレード台帳への追記
```

### 1-1. なぜ週次か

エントリーは T-15（発表15営業日前）で、日次で見ても大半の日は候補が出ない。
一方で**月曜に固定すると、火曜〜金曜に T-15 を迎える銘柄を取りこぼす**。

したがって週次バッチは「その週に T-15 を迎える銘柄をまとめて先に確定させ、
各銘柄の T-15 当日に建てたものとして記録する」方式にする。バッチの実行頻度と
建玉日は別物である点に注意。

### 1-2. 既存資産との関係

- カレンダー再構築は既存の `run_daily.ps1`（TDnet アーカイバ）が毎日
  動いているので、その出力を使う
- スコアリングは投影DB経由（`materialize.py` で毎週作り直す）
- **`writer.lock` による直列化を必ず通す**。日次ジョブと衝突すると
  `database is locked` で落ちる（2026-09-01 に実際に2.5時間を失った）
- **配信遅延の織り込みは不要**。J-Quants は Light 以上なら株価・TOPIX とも
  当日16:30頃に当日分が配信される（12週遅延は無料プラン固有の制限）。
  月曜朝のバッチは前営業日終値と TOPIX 200日移動平均をそのまま参照できる

## 2. forecast_snapshots の凍結（PIT の証拠保全）

**これが設計上いちばん重要な部分。**

ペーパートレードの結果を後から検証するとき、「その時点で本当にそう判断
していたのか」を証明できなければ意味がない。人間の記憶も、再計算した値も
証拠にならない（DBは更新され、訂正短信は過去を書き換える）。

### 2-1. 凍結するもの

判定した瞬間に、以下をそのまま1レコードとして書き出して**二度と更新しない**。

| 項目 | 内容 |
|---|---|
| `snapshot_id` | 一意キー |
| `as_of` | 判定日（この日までの情報だけで判断したという主張） |
| `ticker` | 銘柄 |
| `event_date` | 対象の決算発表予定日（代理日） |
| `scores_json` | S1〜S8 の各スコアと available フラグ、evidence 文字列 |
| `evidence_score` | 合成スコア |
| `inputs_json` | スコアの入力になった単独値・BS項目の実数値 |
| `filing_ids` | 根拠にした書類の id 列（本体DBの `filings.id`） |
| `market_filter` | TOPIX終値・200日移動平均・判定結果 |
| `decision` | entry / skip_full / skip_filter / skip_score |
| `frozen_at` | 書き込み時刻 |

### 2-2. 凍結の原則

- **追記専用**。UPDATE も DELETE もしない。訂正が出ても過去のスナップショットは
  そのまま残す（「当時はそう見えていた」が事実だから）
- `inputs_json` に**値そのもの**を入れる。DBへの参照だけだと、後で値が
  訂正されたときに当時の判断を再現できない
- `filing_ids` は根拠の追跡用。値と参照の両方を持つ

### 2-3. 検証時の使い方

蓄積後、「実際のリターン」と「凍結時のスコア」を突き合わせる。
再計算はしない。**再計算した値と凍結値が食い違ったら、それ自体が発見**
（訂正の影響、あるいはパイプラインの非決定性）。

## 3. 仮想トレード台帳

エントリーからエグジットまでを1行で追える形にする。

| 項目 | 内容 |
|---|---|
| `trade_id` | 一意キー |
| `snapshot_id` | 判断の根拠（2章のスナップショット） |
| `ticker` / `event_date` | |
| `entry_date` | T-15 に相当する営業日 |
| `entry_price_assumed` | **想定約定価格**（後述） |
| `position_size` | 建玉時の想定NAVの10% |
| `exit_rule` | 4分岐のどれで出たか |
| `exit_date` / `exit_price_assumed` | |
| `ret_gross` / `ret_net` | 純は往復コスト0.4%控除後 |
| `topix_entry` / `topix_exit` | 超過リターン計算用 |
| `status` | open / closed |

### 3-1. 想定約定価格の決め方

**バックテストは終値を使っているが、ペーパートレードで終値を使うと
「その日の引けを見てから建てた」ことになりかねない。** 実運用に近い形にする。

- **エントリー**: 判定日の**翌営業日の始値**を想定約定価格とする。
  判定は前日までの情報で行い、寄り付きで建てる、という運用を模す
- **エグジット**: 4分岐の判定日の**翌営業日の始値**
- 始値は `prices.open` に取得済み（2026-08-31 に保存漏れを修正済み）

**これはバックテストとの差異になる。** v2 の実績値と比較するときは
「終値ベース vs 始値ベース」の違いがあることを明示する。差分そのものが
スリッページの実測値になるので、**両方を記録する**（`ret_net_close_basis`
を併記）。

### 3-2. 4分岐のエグジット判定

`module_c/exit_engine.py` の既存ルールをそのまま使う。PTS出来高は
取得できないので `pts_ratio=None` を渡し、「翌日寄り指値」に落ちる
（`calibration_backlog.md` 1-3 で承認済みの fallback）。

## 4. 市場フィルターの作動記録

TOPIX 200日移動平均によるエントリー停止は、**実運用で何回・何日作動したか**を
記録する。バックテストでは32日 / 116イベントだった。

| 項目 | 内容 |
|---|---|
| `date` | 判定日 |
| `topix_close` / `topix_ma200` | 実数値 |
| `allowed` | エントリー可否 |
| `n_candidates_blocked` | その日に止めた候補数 |

**止めたことによる機会損失も測る**。止めた候補について、建てていたら
どうなったかを（実弾ではないので）並行して記録する。フィルターが
役に立ったのか、単に good trade を削っただけなのかは、これでしか分からない。

### 4-1. 運用規則（重要）

**機会損失データを理由に、フィルターを運用途中で変更・停止しない。**
変更は**新しい事前登録を必要とする**。

この記録は「後から評価するための証拠」であって、「走りながら調整するための
ダッシュボード」ではない。反実仮想の損益は常に「止めなければ儲かっていた」
方向に見える瞬間がある（フィルターは下落局面で作動するので、その直後の
反発を取り逃す形になりやすい）。それを見て途中で止めれば、
**前向き検証そのものが後知恵に汚染される**。

止めたくなったら、止めずに記録を続け、期間の終わりに事前登録し直す。

## 5. 蓄積期間と判定

### 5-1. 期間の目安

**2四半期（約6ヶ月）= 動作検証。エッジの合否判定は 4〜6四半期。**
（当初指示の「1〜2四半期で判定」は撤回され、この案が正となった）

根拠: v2 の建玉は5年で334件 = 年間約67件 = 四半期あたり約17件。
1四半期では**統計的に何も言えない**（17件では勝率の差が偶然と区別できない）。
2四半期でも約34件で、まだ足りない。

**したがって「2四半期で合否を出す」設計にはしない。** 2四半期で見るのは
以下の3点に限る:

1. **パイプラインが実運用で動くか**（週次バッチが落ちずに回るか）
2. **凍結スナップショットが証拠として機能するか**
3. **バックテストと前向きで、シグナルの発火率・候補数が同程度か**

期待値や勝率の一致を語るには、**最低でも4〜6四半期（1〜1.5年）**必要。
これは事前に認めておく。焦って少数サンプルで判断しないための予防線。

### 5-2. 判定方法

比較対象は v2 の実績値。

| 指標 | v2 実績 | 前向きで見るもの |
|---|---|---|
| 期待値（純） | +1.47% | 符号と桁が合うか |
| 勝率 | 51.5% | ±5pt 以内か |
| TOPIX超過 | +0.21% | 符号が合うか |
| MDD | -13.84% | **谷の深さの挙動**（基準内に収まるか） |
| 建玉数 | 年約67件 | 発火率が同程度か |

**MDD は特に注意して見る。** v2 の合格が脆弱だった主因がここで、
±3シフトで -19.4% / -24.1% まで悪化した。前向きで -15% を超えるなら、
v2 の -13.84% は過去への適合だったと判断する材料になる。

### 5-3. 判定しないと決めておくこと

- **少数サンプルでの合否**。3-4章の記録が目的であって、
  17件や34件で「効いた/効かなかった」を言わない
- **前向きの結果を見てからのパラメータ調整**。それをやるなら
  新しい事前登録として別途決める

---

## 6. 実装しないこと（明示）

- 実弾の発注機能。**一切作らない**。誤操作の経路を残さない
- 自動売買・証券会社API連携
- 前向きの結果に基づく自動的なパラメータ更新

---

## 7. レビュー観点（この設計書について）

1. 週次バッチの粒度（週次でよいか、日次にすべきか）
2. 想定約定価格を「翌営業日始値」にする判断
3. 蓄積期間の目安（2四半期では合否を出さない、という設計）
4. 凍結スナップショットに含める項目の過不足
5. フィルターの機会損失も測る、という方針
