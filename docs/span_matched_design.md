# span-matched YoY モード 設計書

**状態: 設計のみ。実装はレビュー後。** 作成 2026-09-02。

## 0. 何を直すのか

四半期報告書の廃止（2024-04-01 以後開始の四半期）で、Q2・Q4 が**半期粒度**
（span_q=2）でしか作れなくなった。投影層はこれを「四半期として渡せない」
ものとして落としている。判断としては正しい —— 6ヶ月の値を3ヶ月として渡せば
前期比が壊れる。

しかし結果はこうなった（2026-09-02 実測、`calibration_backlog.md` §7）:

```
候補61件の available シグナル本数: 0本=35件 / 1本=26件 / 2本以上=0件
B3 の評価可能トレード: 334件中 7件 (2.1%)
```

**「四半期として渡さない」という正しい判断が、結果として「何も渡さない」に
なっている。** 制度変更後は半期粒度が唯一の情報なのだから、落とすのではなく
**同じ粒度どうしで比較する**のが筋である。

これが span-matched YoY モードの動機。

## 1. 設計方針

### 1-1. 中核となる考え方

前期比は「3ヶ月 vs 3ヶ月」でなくてもよい。**「6ヶ月 vs 前年の同じ6ヶ月」**
でも意味は保たれる。壊れるのは**異なる長さを比べたとき**だけ。

したがって:

- span_q を落とさず、**span を明示したまま**投影する
- スコアラーは「同じ span・同じ累計点の前年値」とだけ比較する
- 比較相手が見つからなければ従来どおり `available=False`（推測しない）

### 1-2. 二系統で走らせる（時系列切替）

| モード | 対象 | 比較の作り方 |
|---|---|---|
| 従来（quarter モード） | 真の四半期チェーンが続いている期間 | span_q=1 どうしの前年同四半期比 |
| span-matched モード | チェーンが切れた以降の期間 | 同じ span・同じ起点どうしの前年比 |

**銘柄ごと・かつ時系列で切り替える（2026-09-02 確定）**:

> **四半期チェーンが5期連続で切れた時点以降、その銘柄は span-matched
> モードに切り替わる。**

「銘柄ごとに一括で決める」ではない点が重要。同じ銘柄でも
2022〜2024 は quarter モード、2025 以降は span-matched モードになる。
制度変更が特定の時点で起きた以上、切替も時点で起きるのが正しい。

「5期連続」は、スコアラーが要求する5四半期分に合わせた。1期欠けただけで
モードが揺れると、同じ銘柄の時系列が途中でモード混在になって比較不能になる。

どちらのモードで算出したかを**必ず出力に含める**。これを混ぜると、
後から成績を層別できなくなる。

## 2. 変更点1: 投影層（`materialize.py` / `adapter.py`）

### 2-1. span を落とさず渡す

現状 `quarterly_standalone` には span_q=1 の行しか入れていない。これを改め、
**全 span を入れたうえで `span_q` 列を持たせる**。

```
quarterly_standalone に追加:
    span_q          INTEGER NOT NULL   -- 1=3ヶ月 2=6ヶ月 3=9ヶ月 4=12ヶ月
    period_start    TEXT               -- 累計の起点（span の意味を確定させる）
```

`period_start` を入れるのは、span_q だけでは「どこからの6ヶ月か」が
決まらないため。Q2累計の6ヶ月と、Q3-Q4の6ヶ月は別物である。

### 2-2. 既存の別枠コードを壊さないこと

別枠 `data_access.get_pl_series` は span を知らない。**span_q=1 だけを返す
ビューを別途用意**し、別枠にはそれを見せる。span-matched を使うのは
本体側の新しいスコアラーだけ。

```
CREATE VIEW quarterly_standalone_q1 AS
    SELECT * FROM quarterly_standalone WHERE span_q = 1;
```

**別枠のコードは1行も変更しない**という既存方針を維持する。

## 3. 変更点2: スコアラー（S1/S2/S4/S5 を優先）

### 3-1. 対象の選定理由

| シグナル | span-matched 化 | 理由 |
|---|---|---|
| **S1 DSO改善** | 対象 | BS項目（売掛金）÷ フロー（売上）。span を揃えれば比率の意味は保たれる |
| **S2 在庫** | 対象 | 同上。ただし原価の数量/価格分解は元々不能（§1-1）。在庫回転のみ |
| **S4 契約負債** | 対象 | 契約負債(BS) vs 売上(フロー)。span を揃えれば成立 |
| **S5 進捗率** | 対象 | 通期予想に対する累計進捗。**元々累計で見る指標**なので span-matched と相性が良い |
| S3 建仮急増 | 別途検討 | BS同士の比較なので span 非依存。そもそも影響を受けていない可能性 |
| S6 在庫両義 | 別途検討 | 原価分解が不能（§1-1）で、span 以前の問題 |
| S7 / S8 | 別途検討 | 未調査 |

**S5 は最も素直に移行できる。** 進捗率はもともと「累計 ÷ 通期予想」で、
span が長いほど進捗が進むのは当然だから、**前年の同じ span と比べる**のが
本来あるべき形である。現行が四半期チェーンを要求しているほうが不自然。

### 3-2. 比較相手の探し方

```
find_yoy_peer(code, period, q_no, span_q):
    1. 同じ (q_no, span_q) の1年前を探す
    2. 見つからなければ「span は同じだが期末点が違う」候補を探し、
       period_start の月が一致するものだけ許す
    3. どちらも無ければ None を返す（推測しない）
```

2 を入れるのは、決算期変更を挟むと q_no がずれるため。ただし
**期末点の月が違うものは絶対に比べない**（季節性が別物になる）。

### 3-3. 出力に必ず含めるもの

```
{"score": …, "available": True,
 "mode": "quarter" | "span_matched",
 "span_q": 2, "peer_period": "FY2025-Q2",
 "evidence": "…"}
```

`mode` を持たせないと、後から「どちらのモードの成績か」を層別できない。
v2 との比較が意味を持つのは quarter モードの分だけなので、これは必須。

## 4. 変更点3: `forecast()` の span-matched 化（検討）

B3 が判定不能になった原因も同じ（前年同四半期が無い）。

**結論: 対象に含めるべき。ただし優先度は S1/S2/S4/S5 の次。**

理由:

- `forecast()` は「前年同四半期 + 証拠イベント」で次期を予測する。
  前年同**期間**（span-matched）に置き換えても論理は保たれる
- ただし予測は**エグジット判定（4分岐）の入力**であり、エントリー側の
  スコアラーより後段。エントリーが動かなければ検証機会自体が生まれない
- 別枠 `forecaster.py` は変更禁止。本体側に span-matched 版を実装し、
  投影層経由で差し替える形になる（`adapter` と同じ構造）

## 4-2. is_valid=0 機構への依存（明示）

**span-matched 比較は `is_valid=0` の無効化機構に全面的に依存する。**

同じ span の前年値と比べるということは、**その2点のあいだに会社の形が
変わっていないこと**を前提にしている。前提が崩れる3つは、いずれも
既存の無効化機構が捕まえている:

| 無効化理由 | span-matched で何が壊れるか |
|---|---|
| **決算期変更** | 期末が動くと「同じ6ヶ月」が別の6ヶ月になる。季節性が一致しない |
| **連結範囲変更** | 前年と違う会社群を比べることになる。増減が事業ではなく範囲の変化になる |
| **遡及修正** | 前年値が後から書き換わっている。当時の値と比較していない |

したがって:

- **`is_valid=0` の期は span-matched の比較相手にしない**
- 比較相手が無効なら `available=False` を返す（別の期で代用しない）
- 無効化機構が緩めば span-matched の信頼性も同じだけ落ちる。
  **この機構は span-matched の前提条件であり、独立に変更してはいけない**

quarter モードでも同じ依存はあるが、span-matched は比較の間隔が
長くなる分（6ヶ月・12ヶ月）、**会社の形が変わる確率が構造的に高い**。
依存度はより強い。

## 5. 検証方針

### 5-1. エッジの再判定はフォワードのみ

**2022〜2024 のデータで span-matched モードの成績を測ってはいけない。**
その期間は四半期チェーンが揃っており、span-matched を使う必要が無い。
そこで良い成績が出ても、それは「使わない場面での成績」でしかない。

エッジの判定は **v3 シャドウでの前向き検証のみ**。

### 5-2. 2022〜2024 データの使い道は実装健全性チェックに限定

**新旧モードのスコア相関**だけを見る。

```
両モードが算出できる (銘柄, 期) について
  corr(quarter モードのスコア, span_matched モードのスコア)
```

期待するもの: 相関が高い（同じ現象を見ているのだから）。
低ければ **span-matched の実装が別のものを測っている**ということで、
実装のバグを疑う。

**この相関は成績評価には使わない。** 高くても「儲かる」ことの証拠にならない。

### 5-3. 合格基準

span-matched モードそのものの合否基準は、**実装完了後に別途事前登録**する。
この設計書では定めない（先に基準を決めてから実装する、の順序を守るため
基準は v4 事前登録として切り出す）。

## 6. 実装順序（提案）

1. 投影層に span_q / period_start を追加（別枠向けビューで互換維持）
2. `find_yoy_peer` と mode 判定を本体に実装
3. S5 を最初に移行（最も素直・進捗率は元々累計指標）
4. S1 / S2 / S4 を移行
5. 新旧モードのスコア相関を測る（実装健全性チェック）
6. v4 として合格基準を事前登録
7. v3 シャドウに span-matched モードを載せて前向き検証開始
8. `forecast()` の span-matched 化を検討（B3 の再検証はこの後）

## 7. レビュー観点

1. 「同じ span どうしなら前年比の意味は保たれる」という中核の仮定
2. 二系統（quarter / span_matched）を銘柄ごとに自動選択する設計
3. `period_start` を持たせて「どこからの6ヶ月か」を確定させる判断
4. S3/S6/S7/S8 を「別途検討」に回した優先順位
5. 2022〜2024 データをスコア相関だけに使い、成績評価に使わない方針
6. `forecast()` を対象に含めるが優先度は後、という判断

## 8. 実装で判明した事実と、設計への差し戻し（2026-09-02）

§6 の 3〜4（S5 → S1/S2/S4 の移行）を実装した過程で、**設計の前提そのものを
書き換える必要がある事実**が3つ出た。1と2は仕様の穴なので直した。
3は承認済みの規則を変える話なので**未実施・要判断**として残す。

### 8-1. 真の四半期が1本も無い銘柄が 23% ある（修正済み）

`switch_point` は「span=1 の行が5期連続で欠けた時点」を返すが、
**span=1 の行が最初から1本も無い銘柄**では `have` が空になり None を
返していた。None は quarter モードを意味し、quarter モードは span>=2 の
行を全部捨てる。結果、この銘柄群は **S1/S2/S4/S5 から永久に見えなかった**。

    span=1 の売上行が1本も無い銘柄: 774 / 3,379 (22.9%)

切れ目が「無い」のではなく**最初から span-matched でしか見られない**が
正しい。`have` が空なら最初の期から span_matched を返すよう修正した。

### 8-2. 現実のデータは「ある時点で全部半期になる」形をしていない

設計は「制度変更が起きた時点で四半期→半期に切り替わる」を想定していたが、
実データは **Q1・Q2 は span=1 のまま、Q3 が欠け、Q4 が span=2 で来る**
という混在形だった（7018 / 7231 で確認）。

    FY2026-Q1 span1 / FY2026-Q2 span1 / (Q3 なし) / FY2026-Q4 span2

短信は 1Q で3ヶ月、中間で6ヶ月累計（→ Q2 単独が引き算で出る）を開示し、
3Q が無いので下期は半期でしか割れない。つまり**欠け方は「連続」ではなく
「毎年 Q3/Q4 の2期ぶん」**で、5期連続にはならない。承認済みの
CHAIN_BREAK_LEN=5 は、この形の銘柄では**永久に発火しない**。

### 8-3. 【要判断】規則A（時点で切替）と規則B（期ごとに最細粒度）

8-2 の帰結として、比較可能ペア数は次のようになる。

| 規則 | 全期間 | FY2025 以降 |
|---|---|---|
| A: 5期連続で切替（承認済み） | 11,324 | 2,954 |
| B: 期ごとに最も細かい粒度を採り、同じ span の前年と組む | 12,227 | 3,851 |

差は FY2025 以降で **+897 (+30%)**。規則Bの span 内訳は
span1 10,637 / span2 1,469 / span3 121。

**規則Bを既定にはしていない。** 承認された規則Aのままにしてある。
規則Bは「同じ銘柄の時系列に span が混在する」ことを許すので、
承認時に懸念された「モード混在で比較不能」に正面から触れる。
ただし各比較自体は常に同じ span どうしであり、壊れるのは
「異なる期の**スコアを時系列で並べたとき**」に限られる。

採否は事前登録の変更として判断が要る。実装は
`span_runner.score_ticker(policy=...)` で切り替えられる形にしてある。

### 8-4. 別枠の位置ベース比較が返していた誤り（実測）

移行の副産物として、別枠が「5行前＝前年同期」とみなす実装が
実際に何を比べていたかが分かった。

| 銘柄 | 別枠が比較していた組 | 実際の間隔 |
|---|---|---|
| 7231 (S2) | FY2026-Q4 vs FY2022-Q4 | **4年** |
| 7018 (S2) | FY2027-Q1 vs FY2025-Q2 | 約2年 |
| 5607 (S1) | FY2027-Q1 vs FY2024-Q2 | 約3年 |

さらに S5 では、**欠けた四半期をゼロとして累計する**ため進捗率が
本来の半分以下に見え、最大の売りシグナルが出ていた。

    S5 が両実装で available: 2,607 銘柄
      旧が強い売り(<=-0.5) なのに新は中立以上 : 315 (12.1%)
      旧が強い買い(>=+0.5) なのに新は中立以下 : 0 (0.0%)

片側にしか出ないのは機構と整合する（欠けた期をゼロで足せば進捗は
過小にしか出ない）。**S5 は available 率が最も高いシグナル(78%)なので、
この 12.1% はそのまま週次スクリーンの偽シグナルになっていた。**

### 8-5. 新設した不変条件（`screener/tests/test_span_scorers.py`、14件）

- 異なる span を前年ペアにしない / 無効期を比較相手にしない
- 前年ペアが無いとき、別の期で代用せず available=False を返す
- **直近開示より4四半期を超えて古い組は available=False**（`MAX_STALE_Q`）
  —— 間違った相手と比べるのと、古い期の証拠を今の証拠として出すのは
  同じくらい悪い。別枠を直した結果、こちらが「前年ペアが取れる最後の期」
  まで黙って遡る挙動になっていたので塞いだ。
- S5: 欠けた四半期をゼロとして足さない（組み立て不能なら available=False）
- S4: CF と営業利益を同じ期間で比べる（span 合計が4になるまで後ろから取る）
- PIT: as_of 以前に出ていない期は見えない

## 9. 【変更記録】規則A → 規則B（2026-09-02 承認・適用）

### 9-1. 何を変えたか

**変更前（規則A・2026-09-02 午前に承認）**
> 四半期チェーンが5期連続で切れた時点以降、その銘柄は span-matched
> モードに切り替わる。

**変更後（規則B・2026-09-02 午後に承認）**
> 期ごとに**最も細かい粒度**の行を採り、**常に同じ span の前年**と比較する。
> 銘柄単位・時点単位のモード切替は行わない。`mode` は
> 「その比較が span=1 だったか否か」の**記録**として残す。

### 9-2. なぜ変えたか

規則Aは「制度変更がある時点で起き、そこから四半期が全部消える」という
**きれいな制度断絶**を想定していた。実データはその形をしていなかった。

    FY2026-Q1 span1 / FY2026-Q2 span1 / (Q3 なし) / FY2026-Q4 span2

短信は 1Q で3ヶ月、中間で6ヶ月累計（→ Q2 単独が引き算で出る）を開示し、
3Q が無いので下期は半期でしか割れない。**欠け方は「連続」ではなく
「毎年 Q3/Q4 の2期ぶん」**なので、5期連続の条件を満たさない。

つまり規則Aは、それが救うはずだった銘柄群に対して**永久に不発**だった。
承認された規則が悪かったのではなく、**承認時に前提としたデータの形が
現実と違っていた**。前提が違っていたことが実測で確定したので、
前提のほうを直す。

### 9-3. 実測値（変更の根拠）

| 規則 | 比較可能ペア（全期間） | FY2025 以降 |
|---|---|---|
| A: 5期連続で切替 | 11,324 | 2,954 |
| B: 期ごとに最細粒度 | 12,227 | **3,851 (+30.4%)** |

規則Bの span 内訳: span1 10,637 / span2 1,469 / span3 121。

加えて `switch_point` の穴（span=1 が1本も無い 774 銘柄 = 全体の 22.9% が
永久に quarter モードに落ち、span>=2 の行を全部捨てられていた）も
規則Bでは構造的に起こり得なくなる —— モード判定が比較の前提でなくなるため。

### 9-4. 承認時の懸念への回答

懸念は「同じ銘柄の時系列がモード混在になって比較不能になる」だった。
規則Bはこれに正面から触れる。回答は次のとおり。

- **各比較は常に同じ span どうし**であり、YoY の意味は保たれる。
  中核の仮定（§2）は変わっていない。
- 崩れ得るのは「**異なる期のスコアを時系列で並べたとき**」に限られる。
  そのために `mode` / `span_q` / `peer_period` を全スコアの結果と
  週次レポートに出し、**人間が比較の根拠を確認できる**ようにした（§9-5）。
- 連続する期の傾きを使うシグナルは、**同一 span の連鎖を個別に要求する**
  （テストで担保。`test_傾き系は同一spanの連鎖を要求する`）。

### 9-5. 適用範囲

- `span_runner.score_ticker` の既定 policy を `prefer_span` に変更。
  `span_only`（旧規則A相当）は比較実験用に残す。
- S1/S2/S4/S5 の evidence 冒頭に `期 vs 前年期(span=N, mode)` を必ず出す。
- 週次レポートの各候補に「比較粒度」行を追加。

### 9-6. 事前登録上の位置づけ

**これはシグナル定義の変更であり、閾値・重みの再調整ではない。**
係数はすべて別枠から写したまま（S1: 0.20、S2: 0.30/0.20/0.30 と 0.5/0.2/0.3、
S4: 0.5、S5: 0.25）。変更したのは「何と何を比べるか」だけ。
合格基準は **v4 として新規に事前登録**する（`backtest_acceptance_criteria.md`）。
規則Aで取った数字は規則Bの成績として使わない。
